# P8.2 — Unified Catalog & Offer Engine

## Objective
Create one canonical commercial offer layer above Aslal's existing Product and Resource records so each business defines an offer once and exposes it consistently across Website, Partner Marketplace, and Telegram.

## Core rule
Product/Resource is the source of truth. CatalogOffer is the commercial presentation. Channel configuration is the delivery projection.

No channel is allowed to create a second product catalog.

Workspace → Product / Resource → CatalogOffer → Website / Partner Marketplace / Telegram

## CatalogOffer
Each offer belongs to exactly one workspace and references exactly one canonical source: Product or Resource. The API rejects zero-source and multi-source offers.

Commercial fields include customer-facing title, slug, descriptions, publication status, price type, price/currency, CTA, terms, eligibility, ordering, and featured state.

Price types: FIXED, STARTING_FROM, QUOTE, CONTACT.

A fixed-price offer must have a non-negative numeric price.

## Channel projection
CatalogOfferChannel controls whether an offer is published to WEBSITE, PARTNER_MARKETPLACE, or TELEGRAM. Channel records can carry channel-specific headline, description, CTA label, destination, and ordering without changing the canonical source.

## Existing system integration
Website public products first use published WEBSITE offers for the public workspace, with the existing Product catalog as compatibility fallback. Partner Marketplace returns published PARTNER_MARKETPLACE offers alongside program terms. Telegram returns published TELEGRAM offers while retaining legacy product/resource fields during migration.

Offer presentation does not create a second attribution mechanism. Existing P3 referral links and attribution records remain authoritative. Payment continues through P6/P7 controls.

## Business UI
New dashboard page: /dashboard/catalog-offers.

The Unified Catalog & Offer Studio provides business context, Product/Resource source selection, title/slug, commercial description, pricing mode, CTA, terms/eligibility, channel selection, featured state, and channel/status badges.

The page uses the existing products.manage permission boundary.

## Security and isolation
Every admin query is workspace-scoped. A product/resource source must belong to the same workspace as the offer. Public offer queries require an active workspace and explicit channel. Partner and Telegram projections never use a partner's home workspace as a substitute for the business workspace.

## Migration strategy
Existing Products and Resources are preserved. Businesses progressively create offers. The compatibility fallback keeps existing catalog behavior operating while offers are introduced.

## Acceptance criteria
1. Create an offer from exactly one Product or Resource.
2. Reject a source from another business.
3. Reject FIXED offers without a valid price.
4. Reject published offers without a channel.
5. Website receives only published WEBSITE offers.
6. Partner Marketplace receives only published PARTNER_MARKETPLACE offers.
7. Telegram receives only published TELEGRAM offers.
8. Channel copy does not alter canonical source.
9. Cross-business partner participation does not leak offers.
10. Telegram connection A cannot request business B offers.
11. Existing products continue working during migration.
12. Existing P3/P6/P7 attribution and financial controls remain authoritative.
